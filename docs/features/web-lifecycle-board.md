# Web 任务生命周期看板

[文档目录](../README.md) · [功能专题](README.md)

首页 `/` 和 `/board` 提供任务看板，GitHub 工作列表在 `/work`，工作完成时间线在 `/timeline`，
任务大屏在 `/live-display`，提案在 `/proposals`，运行与后台服务信息在 `/operations`。这些视图共用顶部导航，
并沿用浏览器中保存的语言和主题。未选择语言时，界面按浏览器语言选择中文或英文。
Web 默认只读。写入受开关、仓库权限、Origin、CSRF、版本和幂等校验约束。

## 日常操作

卡片显示标题、仓库、状态标签、一句话原因、由谁处理和最新更新时间；可以直接开始或回复的
卡片带快捷按钮。看板顶部的“等你处理”汇总列出需要人处理的任务，点击即可打开。

打开卡片后，详情分三层：

1. **现在怎么样**：一句结论，以及发生了什么、原因（附来源和原文）、影响、谁处理；
   下面是一个主操作，并写明点击后会发生什么、哪些已发布内容会保留。其余操作放在次要按钮里。
2. **走到哪一步了**：按时间排列的任务、发布和 PR 节点，标出当前所在节点。
3. **需要追溯时再看**：执行历史、需求描述、事件时间线和技术信息，默认折叠，
   每一项写明里面有什么。执行历史包含每个 Task 的所有 Attempt、阶段上报、心跳、
   结束时间、脱敏失败原因和日志。

执行阶段来自 Worker 的上报；未上报时明确显示等待信息，不估算完成百分比。
常见错误（PR 快照变化、Worker 进程退出、超时、限流等）显示为易懂的说明，同时保留原文。

看板接口为每张卡片返回 `status_summary`：`state`、`tone`、`owner`、`needs_action`、
`stage`、`attempts`、`cause`、`primary` 和 `since`。页面只用它组织文字，不在前端重新推导状态；
`counts.needs_action` 和 `attention_items` 供顶部汇总和“只看需要我处理”筛选使用。

| 阶段 | 含义 | 下一步 |
| --- | --- | --- |
| 待整理 | 尚未激活的需求 | 编辑、开始或取消 |
| 已排队 | 已请求执行，等待后台调度 | 等待；需要停止时取消 |
| 执行中 | Worker 运行或已有结果正在发布 | 查看阶段和心跳；需要停止时取消 |
| 需要处理 | 执行失败、发布失败、问题、决策或清理失败 | 根据具体原因回复、批准、重试或取消 |
| 待评审 | 已产生 PR，需要评审或后续修改 | 打开 GitHub PR、要求修改或取消 |
| 已完成 | 结果已经满足完成条件，且之后没有失败的执行 | 必要时重新打开；不再需要时取消 |
| 已取消 | 已停止的任务及历史记录 | 使用“已取消”视图查看，不再执行旧操作 |

已通过审核并发布到 GitHub 或 TAPD 的分析方案，没有 PR 且尚未写入工作项完成标记时，
在“待评审”列显示“方案已交付，等待下一步指令”。详情列出对应结果、执行和发布回执，
不计入“等你处理”，也不建议重试实施。发起人可打开来源单据，按现有授权流程要求实施或
继续分析；不需要后续工作时，使用“结束跟踪”（原取消命令），保留已发布报告。
未通过审核、发布未完成、仍有待处理输入、较新的任务或未结束的执行，继续显示原来的状态。
该显示只读取现有记录，不补写完成标记。

执行失败时优先展示该任务的发布前评审、评审或投票轮次错误；轮次未记录错误时读取最近
失败阶段或 Attempt 原因。`process_missing_or_zombie` 单独作为进程观测保留，不覆盖轮次错误。

GitHub 请求的自动分类属于正常执行：等待调度时显示“已排队”，分类运行时显示“执行中”。
初始路由置信度低不会触发人工审批通知；确实需要补充信息或决策时，才进入“需要处理”。

有排队或执行中任务时，看板每 15 秒轮询；空闲时每 45 秒轮询，页面隐藏时暂停。
重叠的自动刷新复用正在进行的请求，手动刷新和筛选变化合并为一次后续刷新。
已打开详情的卡片事实变化时更新详情；事实未变时最多每 60 秒重新读取，
位于保留历史页的已选卡片仍随每次轮询直接读取详情。输入中的回复和修改草稿不会被轮询覆盖。
失败反馈保留在当前对话框中；网络超时会结束等待状态，重试相同请求复用幂等标识。
任务和事件采用游标分页。自动轮询通常只读取首页，并保留已加载的后续任务页；
每 60 秒以及手动刷新时重新读取已加载的页，以核对变化和分页游标。

Web 任务的 Worker 输入保留按顺序记录的原始事件，包括早期回复和问题关联。
短历史直接进入 prompt；超过内联预算时，prompt 要求先读取本次 Attempt 的完整历史文件。
最新回复不会自动覆盖之前仍适用的约束；结果只应声明已处理的事件。

## 回答 Agent 的问题

等待回复的卡片会显示 Agent 提出的可行选项和各自的简短取舍。第一项标为「推荐」。
点击一个选项就提交该答案。选择「以上都不选，自己填写」可打开原有文本输入框。
没有结构化选项的历史问题仍可用文本回答。回复仍绑定打开的那个问题和版本。

## 工作完成时间线

在导航栏打开「时间线」，可按日、周、月浏览，使用日期选择器跳转或按仓库筛选。
日期按浏览器时区划分，每周从星期一开始。周和月视图可点击其中一天查看当天清单。
「复制工作清单」将当前日期范围及仓库筛选下的记录复制为 Markdown，包含项目、需求和已发布的交付链接。

点击一条记录可打开 Agent 收据，查看需求、项目、执行起止时间、耗时、完成时间、验证记录和交付链接。
Worker 在现有交付步骤中另外撰写一到两句短摘要。Robert 脱敏后随执行结果保存，收据直接展示这段文字。
没有可用短摘要的记录会显示提示，原始交接和交付材料仍可从相关入口查看。
执行详情可从收据内的看板入口查看。点击「复制为图片」会生成同一份收据。
浏览器限制剪贴板时可下载 PNG。

用量按同一请求归集到本次结果产生前的运行，包含分类、执行、重试、评审、投票和发布前检查。
运行结束后，Robert 按 Attempt 或阶段运行 ID 保存已上报的用量，日志清理后仍可汇总。监督决策在明确关联到单个任务时计入，
诊断按目标任务计入，Proposer 按获批后实际受理的提案计入。工作流级或全局调用保留自己的记录。
历史运行可从仍可用的已登记日志读取用量。
模型调用在启动检查点记录 pending，随后按实际证据补全 partial、complete 或 unavailable。
排队和产物接纳不新增调用；原生会话恢复单独记录调用段。累计会话用量扣除恢复前的已记录基线，
每次调用上报的增量用量直接计入。Claude 与 Codex 保留各自提供方标签，缺失数据继续显示未上报。
活动统计分别保留排队、模型退出观测、产物保存与登记、实际交付时间，并区分并行活动总和与区间并集；
提供方未给出精确完成时间时，退出观测时间只作为控制器观测证据。
历史任务缺少请求关联时，只统计该任务。收据拆分普通输入、缓存读取、缓存写入和输出，并显示四类数据齐全的运行数。
未上报的类别显示「未上报」，显式上报的零保留为零。费用显示模型适配器或网关上报的美元小计及人民币折算，
并标注参考汇率、日期和来源。默认用 [2026 年 11 月 20 日官方中间价](https://hzf.mofcom.gov.cn/article/zyfw/jrfw/jrfwywzn/jrfwwh/hlfxglzy/202611/9514.html)
（1 USD = 6.7131 CNY）。启动 `robert web run` 时可同时传入 `--receipt-fx-rate` 和 `--receipt-fx-date`
覆盖。覆盖不全时，金额只对应有费用记录的运行。提供方没有上报的金额须另行按其实际计费价格核算。

Codex、Claude、CBC 和 OpenCode 从结构化输出采集用量。配置的自定义模型命令可将计量数据写到
`ROBERT_MODEL_USAGE_FILE` 指向的文件，格式为含 `usage` 和可选 `total_cost_usd` 的 JSON 对象。
`usage` 接受 Anthropic Messages 字段 `input_tokens`、`output_tokens`、`cache_read_input_tokens` 和
`cache_creation_input_tokens`，其中 `input_tokens` 是普通输入。命令应从模型服务的响应提取数据，
该文件与命令的原有业务输出独立。

每条记录对应一次有审核通过结果的已完成任务，日期优先取最后一次发布回执或本地结果记录。
发布了 PR、评审或评论后，即使来源单据还开着，交付也可出现在时间线上。
通过审核的本地结果会显示在清单中，并可从看板查看详情。

## 电视任务大屏

从顶部导航进入「大屏」，点击「全屏」即可投屏。页面每 5 秒刷新一次，展示累计完成、本周完成、今日完成
和正在处理的任务数。完成统计沿用工作完成时间线的口径，日期按浏览器时区计算，每周从周一开始。
「正在处理」统计处于运行状态的任务，包含正在发布结果的任务。

首次加载时展示当前统计。之后每出现一条新完成记录，显示一张执行收据，每张停留 30 秒。
同批多张按完成时间依次展示。连接中断时保留最近一次统计并自动重试，恢复后继续展示新收据。

## 异常恢复

- **执行失败或连续失败**：查看最近一次执行的原因，使用“重试执行”。Web 任务可调整
  Worker；GitHub 来源的失败任务通过现有 retrigger 流程重新验证来源及授权。
  已排队或仍在运行时不重复创建 Worker。
- **已完成后又有执行失败**（例如 PR 评审完成后，多模型评审失败）：任务回到“需要处理”，
  不再显示为已完成。GitHub 来源且满足 retrigger 条件时，主操作是重新运行失败的那一步；
  否则使用“重新打开并运行”。源已关闭时保持已完成。请求重新运行后，任务显示为“已排队”，
  在后台开始执行前不再提供重新打开，避免同时产生两次执行。
  这些任务仍可使用详情中的“取消任务”，包括已经排队的重新执行请求。
- **任务不再需要**：在任务详情使用“取消任务”，确认后归入“已取消”视图。
  曾经完成过的任务也可以直接取消，无需先重新打开。取消会撤销尚未执行的请求，
  保留原有完成记录、执行历史和已经发布的 GitHub 内容。
- **发布失败**：使用“重试发布”，复用已经审核的结果。它不重新执行任务，也不会放宽
  发布审核和幂等规则。一次重试执行结束后，如果仍然失败，可以再次重试。
- **Issue / PR 关闭时 Worker 仍在运行**：原始任务和派生 PR 的执行信息一并展示。
  点击“停止并取消”会检查停止结果；未确认进程组停止时保留运行状态并给出原因。
  后台记录的清理失败也会进入“需要处理”。
- **取消与发布冲突**：仓库已有活跃执行周期时返回冲突，待周期结束后重试。
  取消成功会终止未完成任务、撤销准备中的尝试和待发布动作，并保留已有 GitHub 变更。
  发布与取消通过按任务的进程锁互斥，避免取消已成功却仍发送先前读取的待发布动作。
  GitHub / Git 发布命令超过 60 秒会记录可重试失败，外部调用期间不占用 SQLite 写锁。
- **长时间排队**：查看 `/operations` 的服务状态。Web 只提交请求；后台服务仍需运行，
  并具备可用 Worker、仓库配置和 GitHub 授权。
- **GitHub 任务回复或再次触发**：看板中的回复、要求修改、重试和重新打开会入队新的
  执行请求。后台扫描取得操作之后的 GitHub 正文和状态后，再准备执行；等待期间显示
  “等待后台刷新 GitHub 上下文”，不会持续唤醒空调度。原始 GitHub 事件和历史产物保留，
  新 prompt 同时包含刷新后的正文及看板操作记录。刷新失败、来源关闭或授权失效时停止
  执行并记录具体原因，可在看板检查后重试。

原始 Issue 或 TAPD 单据关闭后，已经交付的 PR 仍然独立跟踪。相关 PR 还在打开状态，
且没有执行、发布或清理问题时，任务留在“待评审”，主操作是打开 PR 等待评审或合并，
不要求取消。原单据关闭期间，看板不提供对该单据的新回复或“要求修改”；后续操作通过
PR 自身的现有授权流程处理。所有相关 PR 合并且剩余工作结束后自动完成；未合并关闭的
PR 保留处理提示。详情仍提供主动取消，供任务确实不再需要时使用。
已记录的 TAPD 关单状态在后续扫描中会继续检查关联交付。只要关单状态相同、
任务归属仍一致且关联 PR 仍使工作项无法结束，就不会重复记录关单审计。
观察到工单重新打开后，下一次关单会重新对账。

源 Issue / PR 的状态来自最近一次后台同步。关闭源不会授权 Web 自动重新打开 GitHub 对象。
缺少进程标识、权限不足或后台长时间占用时，页面会显示失败原因，不会伪报取消成功。

## 在依赖 PR 合并后回复

已认证的 Web 操作员可以为当前问题登记一条待提交的回复。在现有
`POST /api/work-items/{work_item_id}/commands` 请求中使用 `command: reply`、
当前 `expected_version`、原问题的 `expected_event_id` 和回复 `body`。
再提供 `dependency.pr_url`、`dependency.task_id` 与
`dependency.task_updated_at`。任务 ID 和 `updated_at` 来自同一详情页的任务记录。
沿用命令入口的幂等键，重发已受理的请求会返回同一结果。

返回 `waiting_for_dependency` 表示只登记了回复。后台扫描看到同仓库 PR
确实合并后，只保存观察并请求 local drain；local lane 恢复执行后才会对原问题提交一次回复。
扫描阶段和 dry-run 都不会提交回复或创建后继任务。普通回复、取消、任务版本变化会使旧登记
失效。仅关闭的 PR 会继续等待。登记不会扩大原任务的仓库、基础分支或操作范围，
也不会把依赖 PR 的代码导入当前任务。

## 恢复边界

daemon 与本地调度共用 SQLite 执行状态。Worker 身份、发布意图、恢复额度和取消
约束共同控制恢复；只读界面可以查看历史记录，写入入口检查当前执行状态。

- 手动重试创建新的 Task，旧失败任务保留终态与证据。
- 普通 Worker 的一次自动恢复额度耗尽后进入“需要处理”，重启不重置额度。
- 发布结果未知时先核对远端，不能直接重新发布。
- 取消只有在确认 Worker 停止后才完成，迟到结果不会复活任务。

真实任务数据库的离线快照可以验证状态投影、历史和按钮可达性；真实 Worker 停止、再次执行及 GitHub 发布必须在拥有该数据库和进程的执行主机上验证。

## 真实数据与历史日志

- 未指定阶段时，窄窗口优先打开有任务的“需要处理”等阶段；显式选择的空阶段仍会保留。
- 看板执行历史按最近任务、最近尝试排序。每个 Task 先显示 10 次尝试，可继续加载全部记录，自动刷新保留已加载数量和展开状态。
- GitHub 工作详情按尝试折叠阶段和日志，自动刷新保留展开状态，并提供对应看板入口。已结束且来源关闭的工作流不再因历史失败或已跳过发布而留在当前待办；运行、待发布或修复中的记录仍保留关注。
- 日志链接使用具体 `artifact_id`，同时校验所属任务和产物类型，避免历史尝试误打开最新日志。文件缺失时明确显示“当前机器没有此文件”，不显示无法打开的预览入口。SQLite 快照仅含日志引用，查看原始 stdout/stderr 需要同时提供对应 artifacts 文件。

详情中的 **Agent 会话** 展开后才读取数据。默认选择最近一次执行，按从新到旧显示
30 条消息与操作记录，可加载更早的记录。消息支持标题、列表、粗体和代码块；
长消息、命令输出和文件 diff 折叠展示，单段内容最多保留 16,000 字符。
运行中随看板轮询更新最近记录，最短间隔为 15 秒，并保留已经加载的历史和展开状态。
执行事实变化时重新读取；已结束且事实未变的会话最多每 60 秒重新核对一次。
会话刷新合并重叠请求，手动刷新会在当前请求完成后继续执行。
同次执行包含多个模型阶段时，可通过“选择 Agent”查看具体模型记录。

会话优先读取执行主机的 `~/.tcodex/sessions` 或 `~/.codex/sessions`，根据任务和
执行身份验证原始 prompt；模型阶段使用数据库记录的所属执行、prompt 摘要和 stdout thread ID
定位会话。找不到本地 session 时，使用该执行记录的 JSONL stdout。
会话读取是只读操作，不会 resume 或继续执行。只展示消息、公开思考摘要、命令、
工具返回和文件变更，跳过运行配置和原始推理内容。敏感内容过滤后再截断。
文件读取、单页扫描和超大记录均有上限；缺少文件、尚无记录或略过超大记录会明确提示。

## 展示与交付证据

The board uses a neutral shared shell, compact cards, underlined stage navigation,
status dots and horizontal Kanban columns above phone widths. Stage navigation
scrolls to the selected column; background refresh keeps the operator's position.
Historical work lists omit repeated execution-state badges and task UUIDs; the
execution detail still exposes task identifiers, attempts and failure evidence.

The detail's visible lifecycle joins task intake, classification/implementation,
execution counts, publication receipts and recorded PR-merge events. Publication
receipts expose only action type, audit/publication status, timestamps and a
redacted error. A closed PR alone never supplies a merge milestone. Event times
are observation times; worker completion and successful publication are separate
facts. Finished tasks fold their latest worker report, retaining per-attempt
phases and exact artifact links. Missing remote files are described once per
attempt rather than repeated as unusable links.

已完成和已取消项目先在数据库中按原有条件筛选、计数和分页，再为当前页生成完整卡片。活动项目仍按完整生命周期事实分类。默认视图不会因为历史增长而隐藏已完成项目；游标继续按更新时间和项目 ID 倒序排列。
