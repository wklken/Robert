# 新 PR 发布前 Review

[功能专题](README.md) · [现有 PR 的多模型评审](multi-model-review.md)

在仓库的 `routes.new-pr` 下配置 `pre_pr_review.workers`，Robert 会在推分支前审查本地候选提交。未填写时沿用原有新 PR 流程。以下片段使用已在全局 `workers` 中配置的名称。

```yaml
repos:
  - full_name: example/service
    # 保留该仓库已有的 checkout、worktrees、default_branch 和 trusted_actors。
    routes:
      new-pr:
        pre_pr_review:
          workers: [codex_reviewer, claude_reviewer]
```

一个 reviewer 直接产出报告。多个 reviewer 使用同一冻结上下文独立审查，结果全数校验通过后，由列表中的第一个 reviewer 汇总。Robert 直接生成共享变更、规则和运行配置索引；每个 reviewer 独立完成源码和测试审查。实现 Worker 在另一个本地 worktree 逐项处理报告，并验证最终提交。 必需验证必须通过。可选验证可保留原始失败或跳过原因，并说明历史检查的适用性；检查格式、来源和最终提交证据仍按原审计规则核验。已启动的任务保留其审查计划和选定的 Worker。修改配置后，新任务使用更新后的计划。

实现 Worker 在迭代中先运行定向检查，最终候选完成仓库要求的验证。复用通过的检查时，
相关源码、测试、依赖锁文件、配置、命令和运行环境必须与原验证一致，并保留原命令、
退出状态和证据位置。提交钩子实际执行的检查可在仓库规则允许时作为证据；钩子修改文件后，
重新验证受影响内容。验证复用指令不会自动认证证据，也不会绕过提交钩子或省略必需检查。

如果意见处理产生了新提交，Robert 会让配置列表中的第一个 reviewer 对最终 SHA
执行独立定向复核：核实原报告中每一项的处理证据，并检查候选提交之后实际新增的
完整 diff。复核使用已经结束的意见处理工作区，保持只读，不额外创建 detached worktree。
最终 SHA 未变化且没有 finding 时复用原审查证据。有 finding 的延后或驳回处置仍需独立复核，
避免用不改代码的处置绕过发布门禁。

默认步骤为实现、独立 Review、一轮主修复、最终定向复核和交付。最终复核确认真实阻塞项时，
最多再进行一次定向补修和复核，补修从上一轮最终提交继续，保留已有修复。
补修次数持久化，重触发和用户回复不会清零。非阻塞意见可以在有依据的处置与独立复核确认下
延后处理；未解决的真实阻塞项、失败的必需验证仍然阻止发布。

原始实现请求封存为独立文件，完整任务说明与验收讨论传入 Review、主修复和最终复核。
旧轮次缺少这份上下文时保留实现和已完成的修复提交，新建审查快照并补充复核，历史 prompt
和产物保持原样。最终复核无法判断验收要求或定向补修后仍有阻塞时，输出可回复的问题；
问题绑定最终 SHA 和复核证据，可信归属人回复后继续。

复核结果绑定当前轮次、候选与最终 SHA、报告、处置文件和新增 diff 的摘要。阻塞、未知、
缺失 finding、身份不符或失败都不会放行发布。成功的复核文件封存后可以在重启时复用；
暂时性失败受同一阶段重试额度和总截止时间约束。进程存活或身份不明时保留原工作区，
沿用现有停止和恢复流程，不因文件已产出而释放进程或工作区归属。

PR 正文包含 Review 报告、已修复项、未处理项及原因，并注明候选和最终提交。Robert 保存各 reviewer 的原始结果和汇总输入。Reviewer 和汇总共享 `scheduler.model_max_concurrency`，共享准备不启动模型，一个新 PR 任务占用一个普通任务额度。

询问和待决策事项面向最初可信请求的归属人：分配请求使用执行分配的用户，评论请求使用评论触发者，Review 请求使用请求者。归属人与来源事件证据保存在 workstream 元数据中，重试和派生 PR 沿用。PR 作者、仓库所有人及后续评论者不会覆盖归属人。候选 PR 尚未发布时没有 `user.login`，不影响已确认的请求归属人。只有无法确认归属人时才询问 `@wklken`。

配置的 `checkout`、`worktrees` 和数据目录可以通过根目录或祖先目录的软链接访问。新候选审查快照记录真实路径；已有快照中的同一可信根目录别名仍可校验。可信根目录内部的文件和子目录软链接继续被拒绝，审查文件必须位于本轮登记的目录内。

## 失败与恢复

- 审查或处置未完成时，发布门禁保持关闭。进程状态不明时，先停掉残留进程，再用任务取消中的未知启动处置功能确认。
- 暂时性失败按阶段有界重试。汇总失败时，成功的独立 reviewer 结果保持封存。只有输入受损或快照变化时，相应 reviewer 才重跑。完整的失败或中断产物在确认原进程组退出、输入和源码身份一致后，通过原校验并单独记录接纳事实；原失败状态和错误保留。
- 报告渲染、公开脱敏、封存和数据库登记分别保存检查点，登记或交付失败时复用相同输入的已封存报告与处置附录。数据库在公开报告登记前单独保存可信封存 hash；首次封存记录保存前中断时，从原始输入重新渲染、脱敏并精确核对缓存。改变渲染或脱敏代码会重新生成报告，不增加模型调用；源文件、封存文件或处置证据发生变化时拒绝复用。
- 缺少完整产物的中断阶段可使用 Codex/Claude 的显式原生会话恢复。会话须匹配原始 prompt、实际 provider 配置目录及原工作目录，并确认原进程组退出和源码检查点一致。意见处理恢复沿用原 writer 工作区，最终复核也复用该工作区。缺失或损坏的会话历史仅让该阶段按原额度重新执行；启动结果或进程身份不明时仍进入需处理状态。恢复段独立计量，次数跨 Attempt 保留。
- 交付 JSON 包含不支持字段或可恢复的跳过原因格式错误时，单独执行最多三次、每次不超过 120 秒的产物修正。修正必须保持源代码、Git 身份、finding 处置、验证结果和来源不变，并再次通过原校验；无法确定原始事实的损坏 JSON 不允许模型重建验证证据。这些修正不计入业务修复次数。
- 整条流水线使用由各 Worker 阶段预算计算的总截止时间，覆盖实现、并行审查、汇总、两轮修复与复核，并提供最多一小时的共享排队额度。阶段运行计时从获得槽位启动时开始。配置中各阶段均为 4200 秒时，总预算为 34080 秒；单阶段超时和原心跳失联限制继续生效。完整且进程已退出的截止时间检查点可沿现有有界恢复路径继续。
- 任务详情和 Board 执行历史展示候选、最终提交、各阶段尝试和安全错误。手动恢复受现有任务权限、来源状态和进程所有权检查约束。GitHub Retrigger 和 Web Retry 沿用已冻结的审查要求。输入、仓库和分支相同且尚无正式结果时，会复用之前封存的审查轮次。
- GitHub 重触发恢复原分支与登记工作区；分类器生成的分支标识变化不应让同一请求丢失检查点。源请求内容、信任状态、工作区归属与干净状态仍需一致。
- 主干前进时先复验原送审输入，再判断影响。普通文档变更，以及能够构建完整闭合依赖证书的简单声明式 Python 变更，在证明与候选修改无依赖关系且可干净合并时，复用原候选 SHA、snapshot、Review 和汇总，不消耗刷新额度。依赖不完整、动态代码、配置或规则变更会保留已有修复提交，合并当前主干并重新审查、验证；冲突仍需解决。发布时重新计算证书并核对原 reviewed base、当前发布 base 和最终提交，避免陈旧证明放行。
- 公开报告允许完整脱敏的 Cookie 示例。含真实凭据的报告行在公开副本中整体脱敏并再次校验，原始封存审查证据不改写；正常结果提交仍严格拒绝真实凭据。
- 推送和创建 PR 使用已审计的同一结果。若已推分支而建 PR 前发现远端 head 或 base 变化，Robert 保留回执并停止建 PR。创建结果不明确时，对账会核对目标、版本和正文。
- 对启用 Review 的仓库，受限维护任务当前停在维护授权检查。仓库策略同样约束当前任务的后续发布。

模型 CLI 仍使用 Robert 服务账户的权限。生产环境需按现有 Worker 信任规则管理账户和凭据。


实施阶段尚未形成 PR 候选提交时，可以提出需要可信归属人回答的范围决策。
Worker 结果保存输出类型、原任务和 Attempt 身份；Robert 将可回答的问题封存、登记为
阶段产物，再提交范围内的提问评论。登记失败时复用原产物。回复绑定原问题、原请求和
已停止的 writer 源码，继续实施使用已接纳回复的新 prompt，保留历史 prompt 与调用记录。

Review 提问独立于代码发布。主干已经变化或暂时无法读取时，将观测结果作为问题上下文，
不阻断有效问题的提交。读取主干后再次核对原产物摘要、源码检查点和最终复核证据，并在
事务内复查阶段和所有权；继续修改与实际发布时仍执行主干门禁。最终必需检查必须通过，
可选历史失败保留原结果、来源和适用性说明，不通过删改失败证据来修正交接。

新建 base 合并前，检查仓库 Git 作者、提交者及已识别 hook 的运行环境与依赖。
预检不执行 hook、不安装包、不绕过仓库策略；缺失环境条件时，在扣除新刷新次数之前停止。
精确完成的既有合并恢复不依赖新合并环境，无法识别的 hook 依赖形式仍要求核实环境。

兼容性证书也支持依赖完全闭合的无外部依赖嵌套 Python 包、静态 JavaScript/TypeScript
模块及精确不变的 package、构建和 CI 描述。动态导入或配置、外部依赖、安装 hook、规则、
schema 变化和依赖图不完整时仍重新审查。前后端目录不相交不能构成豁免；Docker 构建
安装的开发依赖发生变化时，只有完整影响证据才能复用原 Review。
