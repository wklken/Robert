# Upgrade to the new source layout

The installed `robert` command keeps its existing subcommands and options.
Direct Python callers must switch to the owning modules. Root-level scripts
and module paths have been removed. This layout change requires no database
migration or configuration rewrite.

1. Pause incoming work and any automation that starts or retries tasks. Keep the
   old installation running until active Workers and control children have
   stopped and their results and pending publications have been reconciled.
   A terminal task row or expired lease alone does not prove process exit.
2. Stop the old services and prevent scheduled jobs from starting them during
   the upgrade. For a managed user service, use `robert service stop` and check
   `robert service status`. Stop separate daemons, supervisors, and scripts using
   the mechanism that launched them. Keep the existing database, result spool,
   artifacts, and worktrees.
3. Replace the installation and update any automation that invokes Python
   entrypoints directly. Use the interpreter from that installation. The
   [command matrix](../src/robert_agent/resources/command-matrix.md) lists the
   current commands. For example, use `python -m robert_agent.runtime.scan` for
   scan batches and `python -m robert_agent.runtime.control` for control children.
4. Validate the deployed configuration with `robert config validate` and check
   `robert status`. New attempts receive new prompt paths. A prompt already
   generated by the old installation can still point at a removed script. For
   affected prepared work, confirm the old process has stopped and reconcile its
   pending effects before using the board's Retrigger action for an eligible
   GitHub task or canceling and replacing other affected work. Preserve the old
   prompt as evidence and use the newly generated prompt for execution.
5. Resume the service and scheduling with the existing deployment controls once
   old processes and stale prepared work have been resolved.
